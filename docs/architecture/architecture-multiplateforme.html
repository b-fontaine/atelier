Une application, toutes les plateformes

Étude d'architecture : cœur Rust partagé, interface Flutter, TUI Rust et web en deux parties. État des lieux au 16 novembre 2026.

La recommandation en six lignes

  • Un cœur Rust hexagonal porte le domaine, les cas d'usage, le stockage local et la synchronisation.
  • Flutter l'appelle par flutter_rust_bridge v2 ; votre présentation (BLoC sealed, FSD, injectable) ne change pas.
  • La TUI (ratatui) et le site public appellent le cœur directement, sans pont.
  • Le web se coupe en deux : site public en HTML (Leptos), application en Flutter Web avec le cœur compilé en WASM.
  • La synchronisation est écrite dans le cœur, sur un modèle simple à serveur d'autorité.
  • Une seule spécification Gherkin pilote le cœur, la TUI et Flutter.

Le point le moins sûr est le stockage hors ligne dans le navigateur : il faut un essai avant de s'engager (section 13).

1. Vue d'ensemble

Trois « coques » d'interface partagent un même cœur. Seule Flutter a besoin d'un pont, parce qu'elle est écrite en Dart ; la TUI et le site public sont en Rust et appellent le cœur comme une bibliothèque ordinaire.

2. Les six décisions

① Où s'arrête Rust ?

Aux cas d'usage. La présentation reste en Dart, dans vos BLoC.

Mettre aussi l'état d'écran dans Rust (façon Crux) supprimerait la duplication entre GUI et TUI, mais aucun outil ne le permet avec Flutter : Crux ne génère pas de types Dart vérifié, et aucun projet Flutter en production ne le fait à tester.

Soupape : quand une logique d'écran est complexe (tri, filtres, droits), le cœur renvoie un modèle « prêt à afficher » que BLoC et TUI enveloppent sans le recalculer. jugement

② Quel pont ?

flutter_rust_bridge 2.13.0. Le seul qui couvre les six cibles, web compris, avec async et flux vérifié.

UniFFI pour Dart est expérimental et sans web attesté. Rinf cherche un mainteneur source primaire.

Réserve : un seul mainteneur écrit l'essentiel du projet. On enferme donc le pont dans un crate mince, remplaçable sans toucher au reste.

③ Web applicatif

Flutter Web + cœur en WASM, sur un sous-domaine dédié.

Le pont exige deux en-têtes HTTP d'isolation (COOP et COEP) vérifié. Safari impose la variante stricte require-corp source primaire.

Conséquences : pas de ressource tierce non déclarée, connexion par redirection plutôt que par popup.

④ Web public

Un site HTML séparé, en Leptos.

La doc Flutter le dit elle-même : Flutter Web n'est pas fait pour le contenu indexable, il faut séparer vérifié.

Leptos garde la pile à deux langages et réutilise le cœur tel quel. Jaspr (Dart) et Astro sont deux variantes valables. jugement

⑤ Stockage local

SQLite partout : rusqlite en natif et, si l'essai S2 le confirme, sur le web.

En natif, c'est sans histoire. Dans le navigateur, rusqlite compile désormais en WASM avec un stockage OPFS source primaire, mais son mariage avec le pont n'a pas été essayé à tester.

Trois plans de repli sont prévus (section 5).

⑥ Synchronisation

Un moteur maison dans le cœur.

PowerSync a bien un SDK Rust, mais il ne tourne pas dans le navigateur et ses mainteneurs n'envisagent pas de l'y porter source primaire. L'adopter casserait le cœur unique.

Les CRDT (Loro, Automerge) ne valent le coût que pour de l'édition collaborative simultanée. jugement

3. Le cœur Rust

Architecture hexagonale classique : les dépendances pointent toujours vers le domaine, et chaque couche est un crate distinct, avec une liste fermée de dépendances autorisées.

bridge · tui · web-public les trois points d'entrée ; aucun ne contient de règle métier
core façade : assemble les adaptateurs et expose un point d'entrée unique
application cas d'usage, ports (traits), modèles de lecture ; ignore SQLite, HTTP et Flutter
domain entités, objets-valeur, invariants ; aucune entrée-sortie
adapters implémentent les ports : storage-sqlite, sync-http, platform-*

Quatre règles qui protègent du pont

  • Un seul crate dépend de flutter_rust_bridge : bridge. Si le pont devient intenable, c'est le seul à réécrire.
  • API à gros grain : un appel par cas d'usage, des structures simples en paramètres.
  • Jamais de panique : toute fonction exposée renvoie un Result. Le code généré par le pont tue le processus si le binaire est compilé avec panic = "abort" source primaire.
  • Version épinglée exactement, identique côté Rust, Dart et générateur.

4. Parcours d'une action

Exemple : l'utilisateur crée une note. La flèche pleine est la commande ; la flèche pointillée est le retour, qui passe par un flux et non par la valeur de retour de l'appel.

Attention sur le web : la doc du pont signale que les flux peuvent y être instables vérifié. Chaque flux doit avoir un test web, et le cœur doit offrir une requête ponctuelle équivalente en repli.

5. Hors ligne et synchronisation

Principe : l'application écrit toujours en local d'abord. Chaque écriture enregistre, dans la même transaction, une mutation à envoyer plus tard. Le serveur reste l'autorité.

Le stockage dans le navigateur : trois plans

ALe même adaptateur SQLite qu'en natif, sur le stockage OPFS du navigateur. Un seul onglet à la fois.Si l'essai S2 réussit. Le cœur est alors partagé à 100 %.

6. Le web en deux parties

Les deux besoins sont contradictoires : le site public veut du HTML léger, indexable et libre d'embarquer des services tiers ; l'application veut un environnement isolé pour faire tourner du WASM multi-fil. On les sert donc sur deux origines.

Ce qu'il faut savoir sur Flutter Web aujourd'hui

  • Le mode WebAssembly de Flutter 3.50 n'est actif par défaut que sur Chromium 137 et plus ; Safari et Firefox reçoivent la version JavaScript vérifié.
  • Le pont ne produit du Dart WebAssembly qu'en version bêta 2.14 source primaire. D'ici là, construire l'application web en JavaScript + CanvasKit jugement.
  • Le build web du cœur demande la toolchain Rust nightly source primaire.
  • L'accessibilité est désactivée par défaut et doit être activée au démarrage source primaire.
  • GitHub Pages ne permet pas de fixer les en-têtes ; Cloudflare Pages, Netlify, Vercel et Firebase Hosting le permettent source primaire.

7. Côté Flutter

Vos pratiques restent en place. Ce qui change : le segment « domaine » de chaque tranche ne contient plus de règle métier, puisqu'elles vivent dans Rust.

Feature-Sliced Design

Couches inchangées : app, pages, widgets, features, entities, shared.

Aucun linter FSD officiel n'existe pour Dart source primaire : prévoir un contrôle d'imports maison ou le jeune paquet import_rules.

Clean Architecture par tranche

presentation : BLoC et widgets.
domain : interfaces de passerelle, échecs sealed.
data : seule partie qui importe le pont.

Les BLoC dépendent des passerelles, jamais du pont.

BLoC sans Cubit

Events et states sealed, comme aujourd'hui.

Le linter officiel bloc_lint a une règle prefer_bloc source primaire ; son comportement exact reste à confirmer à tester.

Injection

injectable + get_it, avec deux environnements : passerelles réelles au-dessus du cœur, ou faux en mémoire pour les tests.

L'assemblage des adaptateurs Rust se fait dans Rust, pas dans get_it.

8. La TUI

  • ratatui 0.30 + crossterm, en architecture modèle / message / mise à jour / vue.
  • Elle consomme les mêmes cas d'usage et les mêmes modèles de lecture que Flutter, par appel direct.
  • Parité ou sous-ensemble : c'est une étiquette sur les scénarios (@tui) qui en décide, projet par projet. La CI publie le tableau « scénario × cible », qui mesure la parité réelle.
  • Tests de rendu par instantanés (insta) ; attention, ils ne capturent ni couleurs ni styles source primaire.

9. Une spécification, trois exécutants

Les fichiers .feature vivent une seule fois, à la racine du dépôt. Chaque cible les exécute avec son outil.

Un dialecte commun à respecter

Les deux outils ne lisent pas tout à fait le même Gherkin. Dans les fichiers partagés :

  • un seul bloc Feature: par fichier, pas de doc strings, pas d'étiquette contenant un espace source primaire ;
  • paramètres écrits en clair ("texte", nombres nus) avec l'option literalParameters de bdd_widget_test source primaire ;
  • étapes formulées au niveau métier, pour avoir un sens devant un écran comme devant un terminal.

La double boucle, sur trois étages

  1. Écrire le scénario. Il échoue au niveau du cœur (@core) : rouge.
  2. Boucle TDD dans domain puis application : test unitaire rouge, code minimal, vert, refactor, linters vierges. Répéter.
  3. Le scénario passe au niveau du cœur : vert.
  4. Même scénario côté Flutter (@gui) : rouge.
  5. Boucle TDD sur le BLoC (bloc_test) puis sur les widgets.
  6. Scénario Flutter vert. Même cycle pour la TUI si elle est concernée.
  7. Si le scénario est marqué @e2e : exécution avec le vrai cœur à travers le pont.

Les tests de widgets tournent contre des faux écrits en Dart, pour rester rapides. Le risque qu'ils divergent du cœur est couvert par les scénarios @core, qui prouvent le comportement, et par un petit lot @e2e qui traverse réellement le pont jugement.

10. Design system

Les jetons de design sont décrits une fois, au format standard DTCG (stable depuis octobre 2025 source primaire), puis générés pour chaque cible.

11. Intégration continue et distribution

BuildsWindows, Linux, macOS, Android, iOS, web

Une modification ne fusionne que si tout est vert, sans avertissement de linter, sans scénario en cours et sans dérive de code généré.

  • Compilation du Rust pendant le build Flutter : mécanisme Native Assets de Dart, conseillé par la doc du pont pour les nouveaux projets ; l'ancien outil cargokit n'est plus maintenu en amont source primaire.
  • Runners GitHub nécessaires : Linux, Windows et macOS (obligatoire pour iOS et macOS).
  • Distribution : Fastforge et msix pour le desktop, fastlane pour les magasins mobiles, dist pour les binaires de la TUI. Plusieurs détails d'empaquetage restent à vérifier à tester.

13. Risques et essais préalables

Rien de cette étude n'a été compilé. Six prototypes courts doivent confirmer les points fragiles. À mener en premier : S1 et S4. S2, S3 et S5 conditionnent le web applicatif.

#EssaiSi échec

S2Cœur en WASM avec SQLite persistant ; rechargement de page ; second ongletPlan B ou C de stockage
S3En-têtes d'isolation sur l'hébergeur visé, connexion par redirection, sur SafariMode mono-fil du pont, moins réactif
S4Un même .feature exécuté par cucumber-rs et bdd_widget_testDialecte plus restreint

Risques durables

  • Mainteneur unique du pont. Parade : crate bridge mince. Signal à noter : RustDesk, son plus gros utilisateur public, est resté en version 1 source primaire.
  • Chaîne de build plus longue : deux langages, code généré, toolchain nightly pour le web. Parade : caches et contrôles de dérive.
  • Faux Dart qui divergent du cœur. Parade : scénarios @core et lot @e2e.
  • Briques jeunes : Leptos, Jaspr, native_toolchain_rust, import_rules. Parade : chacune est isolée derrière une frontière et remplaçable.

14. Feuille de route

  1. Squelette du dépôt : workspaces Rust et Dart, linters, CI minimale.
  2. Essais S1 (pont) et S4 (spécification partagée).
  3. Première tranche verticale dans le cœur seul, pilotée par un scénario.
  4. Stockage SQLite natif.
  5. TUI : le même scénario dans le terminal.
  6. Flutter : pont, première tranche FSD, BLoC, scénario d'écran.
  7. Design system : jetons, premiers atomes, Widgetbook ; essai S6.
  8. Synchronisation, avec scénarios de conflit.
  9. Web applicatif : essais S2, S3, S5, puis choix du plan de stockage.
  10. Site public.
  11. Distribution sur chaque cible.

15. Limites de l'étude

  • La recherche principale a vérifié 25 affirmations par vote contradictoire (toutes confirmées). Elles portent sur le pont, Flutter Web, PowerSync, Loro et Crux.
  • Tout le reste (TUI, Gherkin partagé, jetons, CI, distribution, retours d'expérience, alternatives, stockage web) vient de recherches complémentaires lues sur sources officielles, sans contre-vérification.
  • Trois choix sont des jugements et non des faits : garder la présentation en Dart, préférer Leptos, écrire la synchronisation soi-même.
  • Les versions citées sont celles du 16 novembre 2026 ; plusieurs bibliothèques évoluent vite.
