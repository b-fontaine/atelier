Mise en place du dépôt

Du dossier vide au monorepo qui compile : workspace Rust, paquets Flutter, pont entre les deux, et un test qui prouve que l'application appelle le cœur Rust.

Ce que vous obtenez à la fin

  • Un workspace Cargo avec les crates du cœur, la TUI et le pont, propre sous rustfmt et clippy.
  • Un espace de travail Dart avec quatre paquets : application, liaisons du pont, design system, Widgetbook.
  • Un test d'intégration Linux vert, où Flutter appelle une fonction Rust.
  • Un build web de l'application avec le cœur compilé en WebAssembly.

Fiabilité des commandes

rejoué la commande a été exécutée le 21 novembre 2026 dans un dossier vide, sous Linux, avec les versions ci-dessous. essai elle vient d'un prototype validé du dépôt (spikes/). non testé elle n'a pas été exécutée : vérifiez-la dans la documentation de l'outil.

Rien n'a été construit pour iOS, macOS ni Windows. Les versions sont figées volontairement : plusieurs combinaisons plus récentes ne s'installent pas ensemble.

3Workspace Rust

Cargo.toml

[workspace]
resolver = "3"
members = []

[workspace.package]
edition = "2024"
version = "0.1.0"
publish = false

[workspace.lints.rust]
unsafe_code = "deny"
unexpected_cfgs = { level = "warn", check-cfg = ['cfg(frb_expand)'] }

[workspace.lints.clippy]
all = { level = "deny", priority = -1 }
pedantic = { level = "warn", priority = -1 }
unwrap_used = "deny"
expect_used = "deny"
panic = "deny"
Laissez members vide. cargo new y ajoute chaque crate tout seul. La forme à motifs ("crates/*") échoue ici : elle attrape le dossier crates/adapters, qui n'est pas un crate rejoué.

rust-toolchain.toml

[toolchain]
channel = "1.100.0"
components = ["rustfmt", "clippy"]
targets = [
  "x86_64-unknown-linux-gnu",
  "aarch64-linux-android",
  "armv7-linux-androideabi",
  "x86_64-linux-android",
  "wasm32-unknown-unknown",
]

Le numéro de version exact est obligatoire : le pont refuse stable. Ajoutez les cibles Apple et Windows quand vous construirez pour elles.

Créer les crates

for c in domain application sync-protocol core test-support; do
  cargo new --lib --vcs none --name "$PROJET-$c" "crates/$c"
done
cargo new --lib --vcs none --name "$PROJET-storage-sqlite" crates/adapters/storage-sqlite
cargo new --lib --vcs none --name "$PROJET-sync-http"      crates/adapters/sync-http
cargo new --bin --vcs none --name "$PROJET-tui"            crates/tui

Chaque crate hérite d'emblée de l'édition, de la version et des lints du workspace rejoué.

Remplacer le code du gabarit

La fonction d'exemple générée par cargo new --lib ne passe pas les lints stricts. Videz les bibliothèques :

for d in crates/domain crates/application crates/sync-protocol crates/core \
         crates/test-support crates/adapters/storage-sqlite crates/adapters/sync-http; do
  echo "//! $(basename "$d")." > "$d/src/lib.rs"
done

Relier les crates

cargo add -p "$PROJET-application"    --path crates/domain
cargo add -p "$PROJET-core"           --path crates/application
cargo add -p "$PROJET-storage-sqlite" --path crates/application
cargo add -p "$PROJET-storage-sqlite" rusqlite@0.43.0 --features bundled
cargo add -p "$PROJET-tui"            --path crates/core
cargo add -p "$PROJET-tui"            ratatui@0.30.2 crossterm@0.29.0
cargo add -p "$PROJET-tui" --dev      insta@1.49.0
cargo add -p "$PROJET-application" --dev cucumber@0.23.0
cargo add -p "$PROJET-application" --dev tokio --features macros,rt-multi-thread
cargo add -p "$PROJET-application" --dev --path crates/test-support

Le sens des dépendances fait l'architecture : domain ne dépend de rien, application seulement de domain, et la TUI jamais du pont.

Vérifier

cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace

Cargo signale des dépendances « inutilisées » : c'est normal sur un squelette, et cela ne fait pas échouer la commande rejoué.

4Tests de comportement Rust

Ajoutez une cible de test sans harnais à crates/application/Cargo.toml :

[[test]]
name = "bdd"
harness = false
  • Les fichiers .feature vont dans features/, à la racine, en français (# language: fr).
  • Écrivez crates/application/tests/bdd.rs sur le modèle de spikes/s4-gherkin/core/tests/bdd.rs.
Terminez le lanceur par run_and_exit. Avec .run(), le processus rend un code de succès même quand des scénarios échouent : votre intégration continue ne verrait rien essai.
cargo test -p "$PROJET-application" --test bdd

6Le pont Rust ↔ Dart

C'est l'étape la plus délicate. Le pont a son propre paquet Dart (core_bridge) et son propre crate (bridge), pour pouvoir être remplacé sans toucher au reste.

6.1 Intégrer

cd packages/core_bridge
flutter_rust_bridge_codegen integrate \
    --rust-crate-dir ../../crates/bridge \
    --rust-crate-name "${PROJET}_bridge" \
    --integration-backend native-assets
cd ../..

6.2 Corriger ce que l'outil a généré

L'outil crée un crate isolé et une application de démonstration. Sept retouches le font entrer dans le monorepo rejoué.

a. Rattacher le crate au workspace. Ajoutez "crates/bridge" à members dans le Cargo.toml racine, puis :

rm crates/bridge/Cargo.lock crates/bridge/rust-toolchain.toml
ln -s ../../rust-toolchain.toml crates/bridge/rust-toolchain.toml

Le lien est nécessaire : le pont lit ce fichier dans le dossier du crate, sans remonter à la racine. Sous Windows, utilisez une copie.

crates/bridge/Cargo.toml

[package]
name = "atelier_bridge"
edition.workspace = true
version.workspace = true
publish.workspace = true

[lib]
crate-type = ["cdylib", "staticlib"]

[dependencies]
flutter_rust_bridge = "=2.13.0"

[lints]
workspace = true

b. Exempter le code généré. Il contient des unwrap et n'est pas formaté selon l'édition 2024.

crates/bridge/src/lib.rs

//! Pont `flutter_rust_bridge` : seul crate du workspace qui en dépend.

pub mod api;

// Code généré : exempté des lints stricts, qui ne visent que le code écrit à la main.
#[allow(
    unsafe_code,
    clippy::unwrap_used,
    clippy::expect_used,
    clippy::panic,
    clippy::all,
    clippy::pedantic
)]
#[rustfmt::skip]
mod frb_generated;

c. Documenter le code de démonstration. Les lints exigent un commentaire //! en tête de api/mod.rs et api/simple.rs, un /// et #[must_use] sur greet.

d. Relier le pont au cœur.

cargo add -p "${PROJET}_bridge" --path crates/core

e. Nettoyer le paquet Dart. Supprimez lib/main.dart, test_driver/, integration_test/ et le test du gabarit dans packages/core_bridge ; retirez material_ui: any de son pubspec.yaml.

packages/core_bridge/lib/atelier_core_bridge.dart

/// Liaisons Dart du cœur Rust, générées par flutter_rust_bridge.
library;

export 'src/rust/api/simple.dart';
export 'src/rust/frb_generated.dart' show RustLib;

6.3 Générer et brancher l'application

(cd packages/core_bridge && flutter_rust_bridge_codegen generate)
(cd packages/app && flutter pub add "${PROJET}_core_bridge" --path ../core_bridge)
(cd packages/app && flutter pub add dev:integration_test --sdk=flutter)

Relancez generate après chaque modification de crates/bridge/src/api/.

6.4 Prouver que ça marche

packages/app/integration_test/pont_test.dart

import 'package:atelier_core_bridge/atelier_core_bridge.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:integration_test/integration_test.dart';

void main() {
  IntegrationTestWidgetsFlutterBinding.ensureInitialized();
  setUpAll(() async => RustLib.init());

  testWidgets('le cœur Rust répond à travers le pont', (tester) async {
    expect(greet(name: 'atelier'), 'Hello, atelier!');
  });
}
(cd packages/app && flutter test integration_test/pont_test.dart -d linux)
Attendu : « All tests passed! », en une vingtaine de secondes la première fois rejoué.
Le cœur Rust n'est pas joignable depuis un test unitaire. Le même test lancé par flutter test test/… échoue : la bibliothèque native n'est pas chargée rejoué. C'est voulu par l'architecture : les tests de BLoC et de widgets utilisent des passerelles factices, et seul integration_test traverse le pont.

6.5 Trois règles pour l'API du pont

  • Toute fonction renvoie un Result ; jamais de panique.
  • Ni i64 ni u64 : ils n'ont pas le même type Dart en natif et sur le web.
  • Les données affichées se lisent par une requête ; un flux ne transporte que des numéros de version.

Attendu : un dossier web/pkg/ avec le .wasm du cœur, puis « Built build/web ». Environ 30 s puis 20 s rejoué.

En développement, l'application web exige deux en-têtes d'isolation :

flutter run -d chrome \
    --web-header=Cross-Origin-Opener-Policy=same-origin \
    --web-header=Cross-Origin-Embedder-Policy=require-corp

Avant d'ajouter SQLite au cœur, créez ce fichier, sans quoi l'édition de liens web échoue essai :

.cargo/config.toml

[env]
CFLAGS_wasm32_unknown_unknown = "-matomics -mbulk-memory"
Non vérifié dans cette disposition : l'exécution dans un navigateur. Les prototypes l'ont validée avec le pont intégré directement à l'application, pas dans un paquet séparé. Reprenez le harnais de spikes/s2-wasm/e2e/ pour le contrôler.

12Ce que ce guide ne couvre pas

  • iOS, macOS, Windows : les dossiers sont créés, rien n'a été construit. Le pont avec SwiftPM reste à vérifier.
  • Le site public : Leptos n'était pas installé sur la machine de référence. Créez le crate comme les autres (cargo new --bin … crates/web-public), puis suivez la documentation de cargo-leptos non testé.
  • L'intégration continue, la signature et la distribution : voir l'étude d'architecture.
  • Le contenu des crates : ce guide pose la structure, pas le domaine, le stockage ni la synchronisation.
Version pour agent, avec le niveau de preuve de chaque commande et le script de vérification : MISE-EN-PLACE-AGENT.md, même dossier. Architecture : docs/architecture/.
